# Request logs and write lock timing

Use `X-Request-Id` from a response to find the same request in the Laravel application logs. This identifier is generated by the application. The request completion event includes the method, route template when matched, response status and elapsed milliseconds. The event omits request bodies, query values, headers, raw URLs and client IPs. An unmatched request records a null route. Laravel exception logs can use the same request context when an exception is reported during request handling.

The completion event is emitted at `info` for ordinary responses and `warning` for server failures. To collect ordinary requests or investigate contention, set `LOG_LEVEL=info` in the private staging environment and verify retention and output on that host. The application also records `media.cleanup.pending` for retryable file failures and `media.cleanup.deferred` when a cleanup attempt throws. Database audit records continue to track business changes independently.

For requests that use the [shared write transaction](../app/Support/WriteTransaction.php), compare these fields by route with representative concurrent requests using synthetic data:

| Field | Meaning |
| --- | --- |
| `write_mutex_attempts` | Number of attempts to acquire the shared lock in the request |
| `write_mutex_wait_ms` | Total wall time spent acquiring the lock, including the lock query |
| `write_mutex_hold_ms` | Total time from acquisition through transaction completion |

Check successful and rejected writes and distinguish wait from hold time before changing the lock. Compare concurrent sign-in, publishing and media cleanup with the same work done separately. Existing tests establish lock behavior and event fields. A throughput claim needs measurements from a representative environment.
